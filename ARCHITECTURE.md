# RedPanda Launcher: архитектура

## Слои

```text
React / TypeScript (src/components, src/pages)
    ↓ типизированные IPC-функции (src/lib/ipc.ts)
Tauri-команды (src-tauri/src/commands)
    ↓
Прикладной движок (src-tauri/src/engine)
    ↓
Общие механизмы: downloads, security, storage, accounts
```

Новые функции установки контента и скинов используют эти границы. Старые
модули запуска игры, импорта, сборщика модпаков и настроек пока сохраняют
свои публичные команды. Это постепенное изменение архитектуры с сохранением
совместимости; перенос всей кодовой базы не завершён.

## Установка контента

- `commands/content.rs`: только аргументы IPC и вызов движка.
- `engine/content/resolver.rs`: обязательные зависимости Modrinth и CurseForge,
  идентичность по ID проекта, проверка противоречивых версий, лимит графа.
- `engine/content/install.rs`: предпросмотр, снимок файлов, проверка объявленных
  конфликтов Modrinth и выполнение сохранённого плана.
- `dependencies.rs`: совместимая команда для старых потребителей резолвера.
- `InstallPreviewModal.tsx`: один экран подтверждения для обоих каталогов.

Путь установки:

1. Пользователь выбирает версию в каталоге.
2. `preview_mod_install` читает версию игры и загрузчик из реальной сборки,
   разрешает обязательные зависимости и хеширует существующие файлы.
3. Движок определяет действия: установить, заменить файл с тем же именем,
   пропустить уже имеющийся SHA-1. Разные версии одного проекта с разными
   именами файлов требуют ручного устранения конфликта.
4. План хранится только в памяти Rust, максимум 32 плана, срок 10 минут.
   Фронтенд получает непрозрачный ID и описание; адреса загрузок не принимаются
   обратно от фронтенда для выполнения плана.
5. `execute_mod_install` принимает только ID плана. План одноразовый. Закрытие предпросмотра удаляет его из памяти.
   Конфликты блокируют выполнение. Одновременно в сборке выполняется один план.
6. Проверяются настройки сборки и снимок файлов. Все новые файлы сначала
   скачиваются во временную папку с проверкой SHA-1. Перед записью снимок
   проверяется повторно. Файлы записываются через `storage::atomic_write`;
   при ошибке записи уже записанные файлы восстанавливаются из временных копий.
7. Событие `mod-install-progress` содержит ID плана, число завершённых загрузок
   и текущий файл. Другие окна не используют чужой прогресс.

Границы проверки: распознавание существующих модов выполняется по SHA-1 через
Modrinth. Неопознанные файлы и полная проверка конфликтов CurseForge отмечаются
предупреждениями. Анализ `breaks`/`requires` внутри всех JAR пока не реализован.
Необязательные зависимости перечисляются, но автоматически не устанавливаются.
Замена одного файла атомарна; вся сборка не является транзакционной базой данных,
и аварийное завершение процесса между записями может оставить часть изменений.
Старые команды скачивания и сторонние изменения файлов не используют блокировку
новых планов; снимок обнаруживает изменения до записи, но не устраняет все гонки.

## Гардероб

- `commands/skins.rs`: публичные команды без токенов в ответах.
- `engine/skins.rs`: чтение и декодирование PNG, проверка размеров, установка.
- `WardrobeModal.tsx`: выбор файла, Classic/Slim, 3D-превью и назначения.
- `SkinViewer.tsx`: общий рендер с явной моделью или автоматическим определением.

`preview_skin` проверяет настоящий PNG: до 1 МБ, 64×64 или 64×32. Для Slim
нужен 64×64. При применении SHA-256 сверяется с предпросмотром: изменение
PNG на диске требует повторного выбора. Скин возвращается как data URL; произвольные директории не добавляются
в область asset-протокола.

Для Microsoft `apply_skin` обновляет токены через существующий механизм аккаунтов
и отправляет multipart `variant` + `file` в Minecraft Services. Токен остаётся
в Rust, перенаправления этого запроса запрещены. Успех фиксируется после успешного
HTTP-ответа сервиса.

Локальный режим доступен в модовых сборках для всех типов аккаунтов. Если
CustomSkinLoader отсутствует, движок подбирает совместимую версию из Modrinth
и устанавливает её с обязательными зависимостями через тот же движок планов.
Наличие мода определяется по метаданным JAR, а не по имени файла. Уже установленный
мод автоматически не обновляется. Записи `loadlist` и прочие настройки сохраняются;
собственный Legacy-профиль ставится первым и имеет отдельную папку на аккаунт.
Выбор Classic/Slim передаётся в локальный профиль. Локальный скин виден только
на этом компьютере; требуется перезапуск игры. Vanilla без загрузчика не поддерживает
этот путь. Ely.by используется локально, API изменения профиля Ely.by не реализован.

После применения копия PNG и модель сохраняются в `RedPandaLauncher/skins/<account-id>`
для превью в лаунчере. Это копия последнего применённого скина, а не синхронизация
с изменениями профиля, сделанными на сайте или на другом компьютере.

## Правила дальнейших изменений

- Новая предметная логика — в `engine`, IPC-обёртки — в `commands`.
- Пути сборок — через `security::instance_dir` и `safe_join`, имена — через валидатор.
- Секреты читаются только из `accounts` в Rust и не возвращаются в интерфейс.
- Долгие операции — async; хеширование большого числа файлов — `spawn_blocking`.
- Изменения пользовательских JSON — атомарная запись с резервной копией.
- Общие типы и IPC-функции — `src/lib/ipc.ts`, локализация — `src/locales`.

## Проверки

```powershell
npm run build
npm test
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

Rust-тесты покрывают идентичность проектов, несовместимые версии зависимостей,
классификацию файлов по хешу, проверку PNG, модели и сохранение конфигурации
CustomSkinLoader. Проверка реального изменения Microsoft-профиля требует входа
в аккаунт с Java Edition; тесты не изменяют профили пользователя.
